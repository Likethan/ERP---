# CampusOS Enterprise Notification & Communication Architecture

## Overview

The CampusOS Enterprise Notification & Communication Layer (Step 26) provides an event-driven, multi-tenant notification orchestration pipeline for higher-education operations. It orchestrates notification events generated by core academic, attendance, examination, financial, placement, workflow, and case management modules, routing them through configurable policy rules, recipient resolution, template rendering, and delivery adapters.

## Architecture Pipeline

```text
Domain Event (Outbox / Event Ingest)
    ↓
Notification Rule Resolution (Event Type, Module Scope, Priority)
    ↓
Policy Condition Evaluation (Declarative Operators via Step 23 Engine)
    ↓
Recipient Resolution (Direct, Student, Faculty, Staff, Parent, Role, Assignee, Admin)
    ↓
Preference & Policy Verification (Mandatory category bypass, channel opt-outs, quiet hours)
    ↓
Template Rendering & Version Selection (Strict schema, HTML escaping, missing variable detection)
    ↓
Channel Selection (IN_APP, EMAIL, SMS, PUSH)
    ↓
Delivery Tracking & Outbox (Idempotency key enforcement, delivery state tracking)
    ↓
Provider Adapter Dispatch (Generic adapters, Mock adapters, timeout protection)
    ↓
Delivery Attempt Recording & Webhook Updates (HMAC-SHA256 authenticated status callbacks)
    ↓
Retry Backoff / Automatic Suppression / Delivery Analytics
```

## Domain Event Model

Notification events are represented by `NotificationEvent`:

- `event_id`: Unique event UUID.
- `tenant_id`: Mandatory tenant scope for SaaS isolation.
- `event_type`: Canonical event type (e.g., `attendance.low_threshold`, `finance.invoice.issued`, `workflow.task.assigned`).
- `source_module`: Originating module (e.g., `ATTENDANCE`, `FINANCE`, `WORKFLOW`).
- `source_entity_type` & `source_entity_id`: Entity tracking reference.
- `correlation_id`: End-to-end distributed tracing ID.
- `recipient_context_json`: Contextual recipient metadata.
- `payload_json`: Structured event payload for template token replacement.
- `sensitivity_classification`: Data classification (`PUBLIC`, `INTERNAL`, `CONFIDENTIAL`, `RESTRICTED`).
- `status`: Lifecycle status (`PENDING`, `PROCESSED`, `FAILED`, `SUPPRESSED`).

## Recipient Resolution Strategies

The `RecipientResolutionService` resolves recipient identities based on the rule's `recipient_strategy`:

1. **DIRECT**: Explicit user resolved by `user_id` or `email`.
2. **STUDENT**: Resolves `StudentProfile`, retrieving student contact details and validating active enrollment.
3. **FACULTY**: Resolves faculty members associated with courses or departments.
4. **STAFF**: Resolves administrative and departmental staff members.
5. **PARENT**: Resolves verified guardian records linked to the target student.
6. **ROLE**: Resolves active tenant users possessing a specific RBAC role (e.g. `HOD`, `EXAMINATION_OFFICER`).
7. **ASSIGNEE**: Resolves the assigned human task worker from workflow context.
8. **ADMIN**: Resolves active `INSTITUTION_ADMIN` members within the tenant.

All resolved recipients are strictly validated against tenant boundaries (`tenant_id == current_tenant_id`) and account active status.

## Transaction Safety & Non-Blocking Design

- **Transactional Outbox**: Business transactions record domain events within the primary database transaction. Slow or external notification delivery operations are never performed synchronously inside business-critical database transactions.
- **Worker Consumption**: Background workers consume outbox events and invoke `NotificationOrchestrationService.process_domain_event_from_outbox`.
- **Failure Isolation**: A notification delivery failure will **never** roll back completed financial, examination, or academic transactions.
