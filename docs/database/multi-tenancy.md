# CampusOS — Multi-Tenancy & Row-Level Security Strategy

## 1. High-Level Tenancy Philosophy

CampusOS is initially deployed for a single institution, but is architected from Day 1 to serve as a **multi-tenant SaaS platform** hosting hundreds of colleges and universities on shared infrastructure without architectural rewrites.

The primary architectural mandate is:
> **Zero Cross-Tenant Leakage. No data belonging to College A shall ever be accessible to College B.**

---

## 2. Multi-Tenancy Architecture

CampusOS adopts a **Shared Database with Row-Level Isolation (`tenant_id`)** reinforced by **PostgreSQL Row-Level Security (RLS)**.

```text
┌──────────────────────────────────────────────────────────────┐
│                    Client HTTP Request                       │
│    (Authorization: Bearer <JWT> with tenant_id claim)        │
└──────────────────────────────┬───────────────────────────────┘
                               │
                               ▼
┌──────────────────────────────────────────────────────────────┐
│                 FastAPI Tenant Context Layer                 │
│  1. Extract & cryptographically verify tenant_id from JWT.   │
│  2. Store tenant_id in Python asyncio ContextVar.            │
└──────────────────────────────┬───────────────────────────────┘
                               │
                               ▼
┌──────────────────────────────────────────────────────────────┐
│                  SQLAlchemy Session Layer                    │
│  1. Automatically bind tenant_id to all INSERT operations.   │
│  2. Execute: SET LOCAL app.current_tenant_id = :tenant_id    │
│  3. Auto-inject WHERE tenant_id = :tenant_id on queries.     │
└──────────────────────────────┬───────────────────────────────┘
                               │
                               ▼
┌──────────────────────────────────────────────────────────────┐
│                 PostgreSQL RLS Engine (DB)                   │
│  Enforce Row-Level Security policy:                          │
│  tenant_id = current_setting('app.current_tenant_id', true)  │
│  (Blocks cross-tenant data even if SQL query omits WHERE)    │
└──────────────────────────────────────────────────────────────┘
```

## 3. Classification: Tenant-Scoped vs Global Entities

### 3.1 Tenant-Scoped Operational Entities (Mandatory `tenant_id`)
All data generated by an institution's operations must carry `tenant_id: UUID NOT NULL REFERENCES core_institutions(id)`:
- **Core**: `core_campuses`, `core_departments`, `core_programs`, `core_regulations`, `core_batches`, `core_academic_years`, `core_semesters`, `core_sections`.
- **People**: `people_students`, `people_faculty`, `people_staff`, `people_guardians`, `people_user_roles`, `people_student_semester_enrollments`, `people_student_status_history`.
- **Academics**: `academics_subjects`, `academics_curriculums`, `academics_course_offerings`, `academics_course_enrollments`, `academics_timetable_slots`.
- **Attendance**: `attendance_policies`, `attendance_sessions`, `attendance_records`, `attendance_corrections`, `attendance_leave_requests`.
- **Examination**: `examination_terms`, `examination_assessments`, `examination_student_marks`, `examination_results`.
- **Finance**: `finance_fee_categories`, `finance_fee_structures`, `finance_invoices`, `finance_payments`, `finance_receipts`.
- **Placement**: `placement_companies`, `placement_drives`, `placement_positions`, `placement_applications`, `placement_offers`.
- **Campus & Logistics**: `campus_clubs`, `campus_events`, `campus_announcements`, `infrastructure_hostels`, `infrastructure_routes`.
- **Documents & Audit**: `documents_storage_records`, `documents_student_records`, `documents_issued_certificates`, `intelligence_audit_logs`.

### 3.2 Global / System Entities (`tenant_id IS NULL` or Tenant-Agnostic)
- **`people_permissions`**: Fixed system-wide capability catalog (`attendance:records:write`).
- **`people_roles` (when `is_system = TRUE`)**: Default platform roles (`SUPER_ADMIN`, `PRINCIPAL`, `FACULTY`). Note: Custom roles have a `tenant_id`.
- **`people_users`**: Global login accounts. A user belongs to a primary tenant, but their authentication account can span roles across institutions.

## 4. Defense-in-Depth: Dual-Layer Enforcement

### 4.1 Layer 1: Application-Level Interception (SQLAlchemy)

A request entering FastAPI extracts the tenant ID and configures the database session:

```python
# app/core/tenant.py
from contextvars import ContextVar
from uuid import UUID

current_tenant_id: ContextVar[UUID | None] = ContextVar("current_tenant_id", default=None)

def set_tenant_context(tenant_id: UUID) -> None:
    current_tenant_id.set(tenant_id)

def get_tenant_context() -> UUID:
    tenant = current_tenant_id.get()
    if tenant is None:
        raise SecurityException("No tenant context present in request")
    return tenant
```

When an async database connection is opened from the pool, the session sets the PostgreSQL local configuration parameter:

```python
# app/core/database.py
async def set_db_tenant_context(session: AsyncSession, tenant_id: UUID) -> None:
    await session.execute(
        text("SET LOCAL app.current_tenant_id = :tenant_id"),
        {"tenant_id": str(tenant_id)},
    )
```

### 4.2 Layer 2: PostgreSQL Row-Level Security (RLS)

PostgreSQL natively checks the current tenant setting on every table access:

```sql
-- Enable RLS on operational table
ALTER TABLE people_students ENABLE ROW LEVEL SECURITY;

-- Force RLS even for table owners
ALTER TABLE people_students FORCE ROW LEVEL SECURITY;

-- Define tenant policy
CREATE POLICY tenant_isolation_policy ON people_students
    AS RESTRICTIVE
    FOR ALL
    USING (
        tenant_id = NULLIF(current_setting('app.current_tenant_id', true), '')::uuid
    )
    WITH CHECK (
        tenant_id = NULLIF(current_setting('app.current_tenant_id', true), '')::uuid
    );
```

### Why RLS is Crucial
If a developer accidentally writes:
```sql
SELECT * FROM people_students WHERE admission_number = '2024-CSE-001';
```
Without RLS, this query could accidentally return a student from College B if they share the same admission number convention. With RLS active, PostgreSQL transparently appends the tenant predicate at the storage layer, guaranteeing that **no query can see or modify another tenant's data**.

## 5. Composite Uniqueness Rule

Every business identifier in CampusOS is scoped to the tenant. The database schema strictly forbids single-column uniqueness on business codes:

- **INCORRECT**: `UNIQUE(admission_number)`
- **CORRECT**: `UNIQUE(tenant_id, admission_number)`

- **INCORRECT**: `UNIQUE(invoice_number)`
- **CORRECT**: `UNIQUE(tenant_id, invoice_number)`

- **INCORRECT**: `UNIQUE(department_code)`
- **CORRECT**: `UNIQUE(tenant_id, code)`

This allows independent colleges to use their own numbering conventions (e.g., both College A and College B can have `INV-2024-001` or student roll `24CS01`) without database collision.
